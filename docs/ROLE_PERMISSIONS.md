# Roles and permissions

## Roles

| Role | Scope |
| --- | --- |
| `lga_coordinator` | Own assigned LGA only. Creates plans, submits work-day claims, provides evidence, and views own LGA history and reports. |
| `state_coordinator` | All LGAs. Assigns/reviews tasks and plans, verifies work days, generates state reports, and submits them to the Senior Supervisor. |
| `senior_supervisor` | All LGAs and state reports. Performs all State Coordinator supervision functions, reviews state reports, consolidates monthly reports, and shares reports with the Boss. |

The Boss is a report recipient, not an application role or administrator by default.

## RLS model

- `profiles` permits a user to view their own profile; supervisors may view all profiles. Users cannot set their own role or LGA assignment through a client policy.
- `lgas` and `responsibilities` are readable by authenticated application users. Only supervisors can add or alter shared operational library entries; official contract entries remain curator-controlled.
- LGA-scoped plans, tasks, comments, evidence, revisions, working-day records, notifications, and audit events are visible only to their LGA Coordinator and both supervisor roles.
- LGA Coordinators can create and update their own unreviewed planning work, claims, comments, and evidence. Database triggers reject self-approval on both inserts and updates, forged comment roles, evidence-review fields, supervisor-assigned tasks, and privileged report states.
- Supervisors alone can assign tasks, verify evidence and tasks, approve plans and working days, create approval history, promote operational responsibilities, and create report shares.
- Reports are visible to the owning LGA Coordinator for LGA reports and to supervisors for all reports. Shares store only a hashed 256-bit random token plus an expiry and revocation timestamp; no anonymous policy or token-verification endpoint exists yet.
- Audit records are generated by database triggers for sensitive mutations. Ordinary authenticated users cannot insert, update, or delete audit rows.

## Server requirements

RLS does not replace application validation. Server actions and route handlers must validate request payloads, record state transitions, file metadata, and share expiry. Supabase service-role credentials, if ever introduced, must remain server-only and must not be used for normal user requests. SECURITY DEFINER functions use an empty search path, bypass RLS only for narrowly scoped authorization lookups or auditing, and expose only required helper functions to `authenticated`.
